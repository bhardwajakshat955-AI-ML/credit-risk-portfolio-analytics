## 5. Issues found and treatments

### 1. `customers.gender` — 600 rows

- **Found:** 600 rows coded 'M'/'F' alongside 'Male'/'Female'
- **Handled:** Mapped M→Male, F→Female
- **Why:** Same attribute, two spellings; without harmonising, segment counts would be split across four labels
- **Impact:** None on values; gender is used for the fairness check only, never as a model feature

### 2. `customers.years_employed` — 500 rows

- **Found:** 500 missing (5.0%)
- **Handled:** Kept as NaN + added missing flag; model imputes with the training-fold median
- **Why:** 5% is too much to drop and the field is a weak secondary signal; a median keeps the distribution intact and the flag lets the model learn if missingness itself carries risk
- **Impact:** Slight shrinkage of variance in the imputed field; negligible for profiling

### 3. `customers.num_dependents` — 500 rows

- **Found:** 500 missing (5.0%)
- **Handled:** Kept as NaN + added missing flag; model imputes with the training-fold median
- **Why:** 5% is too much to drop and the field is a weak secondary signal; a median keeps the distribution intact and the flag lets the model learn if missingness itself carries risk
- **Impact:** Slight shrinkage of variance in the imputed field; negligible for profiling

### 4. `customers.years_at_residence` — 500 rows

- **Found:** 500 missing (5.0%)
- **Handled:** Kept as NaN + added missing flag; model imputes with the training-fold median
- **Why:** 5% is too much to drop and the field is a weak secondary signal; a median keeps the distribution intact and the flag lets the model learn if missingness itself carries risk

### 5. `customers.annual_income` — 494 rows

- **Found:** All 494 'Unemployed' customers have annual_income > 0 (median ≈ 40.8k)
- **Handled:** Kept as supplied; raised as open question Q2 in the assumptions log
- **Why:** Income may include household / benefit / rental income; no basis in the data to overwrite it
- **Impact:** Income-based segments for the unemployed group should be read with this in mind

### 6. `loan_accounts.interest_rate_pct` — 294 rows

- **Found:** 294 missing (2.0%), spread evenly across loan types
- **Handled:** Raw column kept with NaN + missing flag; `interest_rate_pct_filled` uses the loan-type median for analytics; the model pipeline imputes on the training fold only
- **Why:** Rate is a pricing field that depends mostly on product; loan-type median preserves that structure
- **Impact:** Imputed rows have slightly understated rate dispersion; 2% of rows, so immaterial

### 7. `loan_accounts.collateral_flag` — 0 rows

- **Found:** 0 rows inconsistent with loan_type (Mortgage/Auto ⇒ secured)
- **Handled:** No change needed
- **Why:** Check only
- **Impact:** None

### 8. `loan_accounts.origination_date vs customers.customer_since` — 7,293 rows

- **Found:** 7293 loans (49.7%) originated before the customer relationship start date
- **Handled:** Both dates kept; a flag column records the inconsistency; relationship tenure is NOT used as a model feature
- **Why:** Cannot tell which date is wrong; a tenure feature derived from them would be meaningless for half the book
- **Impact:** Loses a potentially useful 'relationship length' feature; raised as open question Q4

### 9. `bureau_credit.days_past_due` — 689 rows

- **Found:** 689 missing (3.0%), spread evenly across statuses
- **Handled:** Kept as NaN; aggregations skip NaN and a per-customer count of unreported DPD lines is created
- **Why:** DPD for a Closed line is always 0 in the data, but for Active/Written-Off lines the true value is unknown; filling with 0 would understate risk, filling with the mean would invent delinquency
- **Impact:** Customer-level max/mean DPD are computed over reported lines only; a 'dpd_unreported_lines' feature carries the gap

### 10. `bureau_credit.date_closed` — 11,243 rows

- **Found:** 11243 nulls, all on Active lines (structural, not a quality issue)
- **Handled:** Kept as NaT
- **Why:** Null means still open; consistent with account_status
- **Impact:** None

### 11. `bureau_credit.date_closed` — 3,149 rows

- **Found:** 3149 closure dates fall after 2025-12-31 (up to 2029-12-24)
- **Handled:** Set to NaT and flagged; account_status kept as 'Closed'/'Written-Off'
- **Why:** No line was opened after 2025-12-29, so a closure in 2026-2029 cannot be an observed event; the status label is still informative, the date is not
- **Impact:** Closure date is not used as a feature; 'time since closure' features are therefore not built

### 12. `bureau_credit.date_opened` — 22,979 rows

- **Found:** Opened dates run 2018-2025 and are independent of the customer's loan origination dates (≈57% of lines open after the customer's latest loan)
- **Handled:** Treated as a current snapshot for the primary model; a time-filtered sensitivity model is also trained
- **Why:** The table has no 'as-of' date, so true point-in-time reconstruction is impossible
- **Impact:** Main leakage risk — see assumption A3

### 13. `repayment_history.emi_paid / payment_status / days_past_due` — 0 rows

- **Found:** 0 overpayments, 0 status-vs-DPD contradictions, 0 missing values, exactly 12 months per account, max DPD 89
- **Handled:** No change needed; validated that Missed ⇔ emi_paid=0 and On-Time ⇔ DPD=0
- **Why:** Table is internally consistent
- **Impact:** None. The 12-month window with DPD<90 defines the observation window (A1)

### 14. `collections_events.event_date` — 3,875 rows

- **Found:** 3875 of 8635 events (45%) are dated before the loan was originated
- **Handled:** Kept and flagged; collections data is used for portfolio analytics and the account view only, and is excluded from the default model
- **Why:** A collections action cannot precede the loan; the date field is unreliable, and collections activity is in any case a consequence of delinquency (post-decision information) rather than a predictor available at the prediction point
- **Impact:** The model does not benefit from collections signal; analytics on collections intensity are presented without a time dimension

## 6. Outliers that are legitimate signal

- Mortgage loan amounts (up to 444,803) are 20-50× the median personal loan. They are real product differences, not errors, and are kept; exposure-weighted metrics are reported separately from count-based ones for this reason.
- Repayment DPD of 60-89 days and bureau write-offs are extreme values that carry most of the default signal; they are kept untouched and no winsorisation is applied before modelling (tree models are scale-insensitive; the logistic model uses a standard scaler fitted on the training fold).

## 7. Final dataset

- File: `data/processed/loan_level_dataset.parquet` (and `.csv`), shape 14,685 × 92
- Grain: one row per loan account; customer attributes repeat for multi-loan customers.
- Target: `target_default` (1 = defaulted, 0 = performing), loan-level, taken as supplied. Default rate 16.10% loan-level; 21.59% of customers have at least one defaulted loan.
- Schema: raw loan + customer columns, `*_missing` flags, `bureau_*` (customer-grain snapshot), `bureau_tf_*` (time-filtered sensitivity variant), `rep_*` (account-grain repayment), `col_*` (collections, analytics only), context ratios (`emi_to_income`, `loan_to_income`, `customer_n_loans`, `customer_total_exposure`) and bands (`income_band`, `age_band`). Full definitions: `reports/feature_dictionary.md`.
- Exposure definition used throughout: `loan_amount` (originated amount). `rep_balance_m12` is shown as the outstanding balance at the prediction point where relevant. See assumption A6.
